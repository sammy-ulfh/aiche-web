## Decisión suelta — Redirección de rutas no previstas (2026-09-02)

| ID | Decisión | Alternativas | Motivo | Estado |
|---|---|---|---|---|
| D-184 | **Las rutas no previstas redirigen a `/404.html` con un 302 del propio host** (routing rule de S3: `HttpErrorCodeReturnedEquals: 404` → `ReplaceKeyWith: 404.html`, `HttpRedirectCode: 302`), más `Documento de error = 404.html` como red de seguridad para el resto de errores 4XX. **El repo no cambia**: `src/pages/404.astro` se queda como estaba | Un `<script is:inline>` con `location.replace('/404.html')` en `404.astro` (implementado y **revertido**); dejar el comportamiento por defecto (servir el 404 en la URL pedida) | El host es un **bucket S3 con website hosting** (`[PENDIENTE-USUARIO]` D-003 resuelto de hecho). El intento por JS no llegaba a ejecutarse nunca: sin `Documento de error` configurado, S3 responde a una clave inexistente con su propio error genérico y **el HTML del sitio no se sirve**, así que no hay script que corra — «If there is no routing rule and the HTTP error 404 occurs, the error document that is specified in the configuration is returned» (AWS, *Configuring a custom error document*). La routing rule lo resuelve en el servidor: redirección real con cambio de URL, sin depender de JavaScript y **sin excepción a la regla 3** — por eso se retira el script. Requisitos: usar el *website endpoint* (`bucket.s3-website-<región>.amazonaws.com`); el REST endpoint (`bucket.s3.<región>.amazonaws.com`) ignora index document, error document y routing rules. El nombre `404.html` distingue mayúsculas y el objeto va en la raíz del bucket. Efecto lateral aceptado: la regla dispara ante **cualquier** 404, incluido un asset ausente, que acabaría redirigido a la página de 404; con el build actual (CSS inline y assets con hash) no falta ninguno. Contrapartida ya aceptada: `/404.html` responde 200, luego para un buscador es un **soft 404**; la página sigue con `noindex` y fuera del sitemap | Aceptada |
| D-185 | **Mientras el sitio sea una preview pública, `robots.txt` es `Disallow: /` y no anuncia el sitemap.** Lo controla `previewNoIndex` en `src/data/site.ts`, que el hook `astro:build:done` de `astro.config.mjs` lee para elegir entre dos cuerpos | Un `robots.txt` estático a mano en `public/` (rompería D-183); `noindex` en todas las páginas; no hacer nada | La preview vive en un bucket de S3 y `siteUrl` sigue siendo `aichegdl.example.com`: si un buscador la rastrea, indexa contenido cuyo `canonical`, `og:url` y JSON-LD apuntan a un dominio que no existe, y limpiar eso después cuesta más que evitarlo. El interruptor vive en la **misma línea de datos que el dominio**, así que el día del lanzamiento se cambian los dos a la vez y no hay forma de acordarse de uno y no del otro. Verificadas las dos ramas del build: `true` → `Disallow: /` sin `Sitemap:`; `false` → el `robots.txt` de siempre con el `Sitemap:`. Alcance conocido: `robots.txt` frena el **rastreo**, no garantiza que una URL enlazada desde fuera no aparezca en resultados; el `noindex` global se descarta a propósito porque es justo lo que no se puede olvidar encendido al lanzar | Aceptada |
